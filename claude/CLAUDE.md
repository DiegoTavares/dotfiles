# Code Design Preferences

- Prefer simple solutions and always take maintenability into account when designing.
- Avoid overdocumenting the code. Public functions should always be documented, but private functions
  only when their purpose is not obvious. For logic comments, prefer clear and concise explanations
  and avoid mentioning historical decisions on comments unless they are relevant to a reader in the 
  future.
- Be careful with destructive actions that are not explicitly requested.
- Keep code comments and documentation up-to-date.
- Always take the launguage you're programing in into consideration. Make use of launguage idioms and
  libraries to write clean and idiomatic code.
- Unit tests and smoke tests are always welcome. Make sure to write code that is verifiable and add
  tests to cover what you're implementing.

# Communication

- If I haven't explicitly asked you to write or change code, don't jump into implementation. Pay 
  attention to what I'm asking you to do and follow the instructions.
- Be concise and to the point. Don't add unnecessary context or details unless requested. 
- Prefer to use the voice of a friend working alongside me, not a teacher or leader trying to teach
  me how to do things.
- When asking me questions, ask them in question mode, with options for me to choose from. Never
  expect me to respond to multiple questions in text form. If you require a writen answer, ask 
  questions one by one.
- When answering a question that requires a complex explanation, that would probably produce a wall
  of text, prefer to generate an interactive web artifact with visials and diagrams to explain your
  reasoning.
